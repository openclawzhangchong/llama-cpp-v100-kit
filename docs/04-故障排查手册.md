# 04 · 故障排查手册

> 排查顺序：**先看报错在哪一步**，再对照下表。llama.cpp 启动分三阶段，
> 报错出现在哪个阶段基本就锁定了原因。

```
阶段 1  解析参数 / 读模型文件    -> 报错多是路径、文件名、参数写错
阶段 2  初始化 CUDA 后端        -> 报错多是驱动 / 架构 / 编译方式问题  ← 本仓库的主战场
阶段 3  把权重装进显存并推理    -> 报错多是显存不够
```

**快速分辨：** 如果黑窗口里连 `listening on http://...` 都没出现就崩了，
看崩之前最后几行有没有 `ggml_cuda`、`CUDA error` 字样 —— 有就是阶段 2。

---

## 一、阶段 2：CUDA 后端起不来（本仓库要解决的核心）

| 报错原文 | 含义 | 解法 |
|---|---|---|
| `the provided PTX was compiled with an unsupported toolchain` | 包是用比驱动更新的 CUDA 编的，PTX 版本太新 | 换本仓库产物（CUDA 12.2 编的），或升驱动 |
| `CUDA error: invalid device function` | 常见于 V100/TCC 上 PDL 检查误报 | 确认脚本里有 `set GGML_CUDA_PDL=0` |
| `no kernel image is available for execution on the device` | 包里没有你这个架构的机器码 | 重新编译并带 `-DCMAKE_CUDA_ARCHITECTURES=70` |
| `CUDA error: out of memory`（加载阶段就报） | 权重装不下，或显存被别的进程占着 | 见第四节 |
| `failed to load CUDA backend` / `ggml-cuda.dll not found` | 后端 DLL 缺失（动态后端模式下） | 用本仓库的单文件版（`GGML_BACKEND_DL=OFF`），没有这个依赖 |

### 怎么确认你的包到底带了什么机器码

```bat
cuobjdump --list-elf llama-server.exe     :: 找 sm_70
cuobjdump --list-ptx llama-server.exe     :: 看 PTX ISA 版本
```

没有 `cuobjdump` 就用 `docs/01` 第五节的 Python 扫描脚本，纯读文件也能看出来。

### 自检：这张卡该配哪个 CUDA 版本

| 驱动版本 | 驱动支持的 CUDA | 该用的编译工具链 |
|---|---|---|
| 452.x – 535.x | 11.x – 12.2 | CUDA **11.8** 或 **12.2** |
| 536.x – 550.x | 12.2 | CUDA **12.2** ← 本默认 |
| 551.61 – 570.x | 12.4 – 12.8 | CUDA 12.4 也行，或直接用官方包 |
| 580+ | 12.9 / 13.x | 官方包即可，不需要本仓库 |

## 二、阶段 1：参数 / 文件问题

| 现象 | 原因 | 解法 |
|---|---|---|
| 双击黑窗**一闪就消失** | bat 编码被改坏了（保存成了 UTF-8，或换行变成了 LF） | 用 `tools/gen-bats.py` 重新生成；**必须在 cmd 窗口里手动跑一遍看报错** |
| `[错误] 找不到模型文件` | `.gguf` 不在 `models\`，或文件名对不上 | 核对文件名，或改脚本里的 `set "MODEL=models\xxx.gguf"` |
| `error: invalid argument: --xxx` | 参数名该版本不支持 | `llama-server.exe --help` 查实际参数名 |
| `[错误] 检测到 8080 端口已被占用` | 已经有一个服务在跑 | 关掉旧黑窗口，或双击 `stopall.bat` |
| 加载完卡住不动 | 模型太大在换页，或磁盘太慢 | 等 1–2 分钟；确认是 SSD |
| 中文乱码 | bat 被存成 UTF-8 | 同上，用生成器重出 |

### 怎么在 cmd 里手动跑一遍看报错

```bat
cd /d D:\llamacpp\scripts
start-server-Qwen3827b.bat
```

窗口会停在那里，报错就能看见了，截图发出来即可。

## 三、阶段 2 之硬件：显卡根本没被系统认到

**这一类问题跟 llama.cpp 一点关系都没有**，但现象很像，必须先排掉。

| 现象 | 检查 | 处理 |
|---|---|---|
| `nvidia-smi` 报 `couldn't communicate with the NVIDIA driver` | 设备管理器看 V100 状态 | 见下 |
| 设备管理器显示**代码 10 / STATUS_INSUFFICIENT_RESOURCES** | 这是 PCIe 资源分配失败 | **BIOS：`Re-Size BAR Support` 关闭、`Above 4G Decoding` 开启**；插 CPU 直连的 PCIEX16 槽；PCIe 速度定 Gen3 |
| 设备管理器显示**代码 43** | 驱动没起来 | 重装/换驱动分支；确认是 Data Center(Tesla) 驱动包 |
| 设备管理器完全没有这张卡 | 供电/金手指/插槽 | 断电重插、清金手指、确认 2×8pin 供电 |
| 有卡但跑起来极慢、GPU 占用 0 | 跑到 CPU 上了 | 看启动日志有没有 `offloaded 0/65 layers`；确认 `-ngl 99` 且 CUDA 后端真的起来了 |

> V100 装在消费级主板上的 BIOS 细节、以及本机踩过的完整坑，见
> **`docs/05-硬件与驱动实战记录.md`**。

## 四、阶段 3：显存不够

判断方法：看 llama-server 打印的显存占用（`CUDA0 model buffer size` / `KV self size`）。

**按性价比排序的处理办法：**

1. **先确认没有第二个服务在跑** —— 一个服务就能吃掉全部显存，这是最常见的原因。
   `stopall.bat` 或任务管理器里结束所有 `llama-server.exe`。
2. **降上下文**（`-c`）：KV 缓存与上下文线性相关。比如 256K → 128K 直接省一半 KV。
3. **KV 缓存量化**：`-ctk q8_0 -ctv q8_0`（**必须同时保持 `-fa on`**），通常能省 40–50%。
4. **换更小的量化模型**：Q4_K_M → IQ4_XS → Q3_K_M。
5. **减 `-ngl`**：把部分层留在 CPU。**速度会明显下降，作为最后手段。**

> 注意：显存不是"越小越好"。留 1–2 GB 余量给上下文增长和计算临时缓冲，
> 顶到 99% 反而容易在中途 OOM。

## 五、功能类问题

| 现象 | 原因 |
|---|---|
| 多轮对话答非所问、格式错乱 | `--jinja` 被删了。思考型模型和多轮对话都需要它 |
| 思考过程显示成普通回答 | 用官方界面看不出 `reasoning_content` 字段；用本仓库 `webui/index.html` 会把思考折叠起来 |
| 局域网其他设备连不上 | ① 服务只听 `127.0.0.1` → 用 `LAN-Launcher.bat`；② 防火墙没放行 → 该脚本会自动加规则，但需要管理员权限 |
| API 调用返回模型名不对 | 改 `--alias` 后的名字 |
| 换了模型但界面还显示旧名字 | 浏览器缓存，`Ctrl+F5` 强制刷新 |

## 六、给别人报错时请附上这三样

1. 黑窗口**完整截图**（从启动到报错）
2. `nvidia-smi` 的输出
3. 你双击的是哪个脚本、选的第几档
