# 04 · 故障排查手册

> 排查顺序：**先看报错在哪一步**，再对照下表。llama.cpp 启动分三阶段，
> 报错出现在哪个阶段基本就锁定了原因。

```
阶段 1  解析参数 / 读模型文件    -> 报错多是路径、文件名、参数写错
阶段 2  初始化 CUDA 后端        -> 报错多是驱动 / 架构 / 编译方式问题  ← 本仓库的主战场
阶段 3  把权重装进显存并推理    -> 报错多是显存不够
```

**快速分辨：** 如果黑窗口里连 `listening on http://...` 都没出现就崩了，
看崩之前最后几行有没有 `ggml_cuda`、`CUDA error` 字样 —— 有就是阶段 2。

---

## 一、阶段 2：CUDA 后端起不来（本仓库要解决的核心）

| 报错原文 | 含义 | 解法 |
|---|---|---|
| `the provided PTX was compiled with an unsupported toolchain` | 包是用比驱动更新的 CUDA 编的，PTX 版本太新 | 换本仓库产物（CUDA 12.2 编的），或升驱动 |
| `CUDA error: invalid device function` | 常见于 V100/TCC 上 PDL 检查误报 | 确认脚本里有 `set GGML_CUDA_PDL=0` |
| `no kernel image is available for execution on the device` | 包里没有你这个架构的机器码 | 重新编译并带 `-DCMAKE_CUDA_ARCHITECTURES=70` |
| `CUDA error: out of memory`（加载阶段就报） | 权重装不下，或显存被别的进程占着 | 见第四节 |
| `failed to load CUDA backend` / `ggml-cuda.dll not found` | 后端 DLL 缺失（动态后端模式下） | 用本仓库的单文件版（`GGML_BACKEND_DL=OFF`），没有这个依赖 |

### 怎么确认你的包到底带了什么机器码

```bat
cuobjdump --list-elf llama-server.exe     :: 找 sm_70
cuobjdump --list-ptx llama-server.exe     :: 看 PTX ISA 版本
```

没有 `cuobjdump` 就用 `docs/01` 第五节的 Python 扫描脚本，纯读文件也能看出来。

### 自检：这张卡该配哪个 CUDA 版本

| 驱动版本 | 驱动支持的 CUDA | 该用的编译工具链 |
|---|---|---|
| 452.x – 535.x | 11.x – 12.2 | CUDA **11.8** 或 **12.2** |
| 536.x – 550.x | 12.2 | CUDA **12.2** ← 本默认 |
| 551.61 – 570.x | 12.4 – 12.8 | CUDA 12.4 也行，或直接用官方包 |
| 580+ | 12.9 / 13.x | 官方包即可，不需要本仓库 |

## 二、阶段 1：参数 / 文件问题

| 现象 | 原因 | 解法 |
|---|---|---|
| 双击黑窗**一闪就消失** | bat 编码被改坏了（保存成了 UTF-8，或换行变成了 LF） | 用 `tools/gen-bats.py` 重新生成；**必须在 cmd 窗口里手动跑一遍看报错** |
| `[错误] 找不到模型文件` | `.gguf` 不在 `models\`，或文件名对不上 | 核对文件名，或改脚本里的 `set "MODEL=models\xxx.gguf"` |
| `error: invalid argument: --xxx` | 参数名该版本不支持 | `llama-server.exe --help` 查实际参数名 |
| `[错误] 检测到 8080 端口已被占用` | 已经有一个服务在跑 | 关掉旧黑窗口，或双击 `stopall.bat` |
| 加载完卡住不动 | 模型太大在换页，或磁盘太慢 | 等 1–2 分钟；确认是 SSD |
| 中文乱码 | bat 被存成 UTF-8 | 同上，用生成器重出 |

### 怎么在 cmd 里手动跑一遍看报错

```bat
cd /d D:\llamacpp\scripts
start-server-Qwen3827b.bat
```

窗口会停在那里，报错就能看见了，截图发出来即可。

## 三、阶段 2 之硬件：显卡根本没被系统认到

**这一类问题跟 llama.cpp 一点关系都没有**，但现象很像，必须先排掉。

| 现象 | 检查 | 处理 |
|---|---|---|
| `nvidia-smi` 报 `couldn't communicate with the NVIDIA driver` | 设备管理器看 V100 状态 | 见下 |
| 设备管理器显示**代码 10 / STATUS_INSUFFICIENT_RESOURCES** | 这是 PCIe 资源分配失败 | **BIOS：`Re-Size BAR Support` 关闭、`Above 4G Decoding` 开启**；插 CPU 直连的 PCIEX16 槽；PCIe 速度定 Gen3 |
| 设备管理器显示**代码 43** | 驱动没起来 | 重装/换驱动分支；确认是 Data Center(Tesla) 驱动包 |
| 设备管理器完全没有这张卡 | 供电/金手指/插槽 | 断电重插、清金手指、确认 2×8pin 供电 |
| 有卡但跑起来极慢、GPU 占用 0 | 跑到 CPU 上了 | 看启动日志有没有 `offloaded 0/65 layers`；确认 `-ngl 99` 且 CUDA 后端真的起来了 |

> V100 装在消费级主板上的 BIOS 细节、以及本机踩过的完整坑，见
> **`docs/05-硬件与驱动实战记录.md`**。

## 四、阶段 3：显存不够

判断方法：看 llama-server 打印的显存占用（`CUDA0 model buffer size` / `KV self size`）。

**按性价比排序的处理办法：**

1. **先确认没有第二个服务在跑** —— 一个服务就能吃掉全部显存，这是最常见的原因。
   `stopall.bat` 或任务管理器里结束所有 `llama-server.exe`。
2. **降上下文**（`-c`）：KV 缓存与上下文线性相关。比如 256K → 128K 直接省一半 KV。
3. **KV 缓存量化**：`-ctk q8_0 -ctv q8_0`（**必须同时保持 `-fa on`**），通常能省 40–50%。
4. **换更小的量化模型**：Q4_K_M → IQ4_XS → Q3_K_M。
5. **减 `-ngl`**：把部分层留在 CPU。**速度会明显下降，作为最后手段。**

> 注意：显存不是"越小越好"。留 1–2 GB 余量给上下文增长和计算临时缓冲，
> 顶到 99% 反而容易在中途 OOM。

## 七、自己重编时可能遇到的坑（GitHub Actions）

换电脑想重新出一版产物，走仓库的 Actions 即可：`Actions` → `Build llama.cpp for Windows` → `Run workflow`。
下面是实测踩过的坑，都已经在流水线里修好了；如果你改了工作流后又踩到，可以对照这里。

### 7.1 点了 Run，秒级失败，而且**一个 job 都没有**

**症状**：run 显示 failure，点进去 `jobs` 是空的（created 和 updated 时间几乎相同）。

**原因**：`run:` 块里用了 PowerShell 的 here-string。它的结束符 `"@` **必须顶在行首**，
而 YAML 的块标量遇到**行首未缩进的行就结束**。两者冲突 → 整个工作流文件解析失败。

**解法**：不要用 here-string，改成数组拼接：

```powershell
$lines = @('第一行', "第二行 $env:X", '第三行')
[IO.File]::WriteAllText($path, ($lines -join "`r`n"), [Text.Encoding]::GetEncoding(936))
```

### 7.2 编译明明成功（`[646/646]`），却死在一句「打印体积」上

**症状**：日志里 `[1/5]`…`[646/646] Linking` 全绿，然后突然报
`Cannot bind parameter 'ForegroundColor'. Cannot convert value "0.01025390625" to type System.ConsoleColor`。

**原因**：写成了 `Write-Host "体积: {0:N1} MB" -f (...)`。`-f` 是 `-ForegroundColor` 的合法缩写，
PowerShell 优先按**参数绑定**处理，于是把体积数字往颜色枚举上转。

**解法**：加一对括号，让它变成表达式而不是参数：

```powershell
Write-Host ("体积: {0:N1} MB" -f ((Get-Item $exe).Length/1MB))
```

### 7.3 产物里少了 CUDA 运行时 DLL

**症状**：打包目录缺 `cudart64_12.dll` / `cublas64_12.dll` / `cublasLt64_12.dll`，启动即闪退。

**原因**：`Get-ChildItem $dir -Include "*.dll" -File` —— `-Include` 只在**路径带通配**或加了
`-Recurse` 时才生效，否则**不报错、直接返回空**。

**解法**：改用 `Where-Object` 过滤（最稳）：

```powershell
Get-ChildItem $dir -File | Where-Object { $_.Name -match '^(cudart64_|cublas64_|cublasLt64_|nvJitLink_|nvrtc64_).*\.dll$' }
```

CUDA 12.x 里 `cublasLt` 还依赖 `nvJitLink_*.dll`，别漏。

### 7.4 怎么确认产物真的带了你那张卡的机器码

流水线会自动跑一遍体检，日志里有一张表：

```
产物                    真机码SASS    PTX
ggml-cuda.dll           sm_70         sm_70
```

（本工作流是 `GGML_BACKEND_DL=OFF` 单文件模式，但 CUDA kernel 实际仍落在 `ggml-cuda.dll` 里，所以体检脚本会把 `build\bin` 下所有 >1MB 的 exe/dll 都扫一遍。）

- **真机码里有 `sm_70`** → 最好，老驱动直接执行，不用 JIT。
- **只有 PTX 里有 `sm_70`** → 也能用。CUDA 12.2 工具链生成的 PTX ISA 是 8.2，536.25 驱动读得懂，只是首次加载慢一点。
- **两边都没有** → 架构参数没生效，这个包对 V100 不可用（流水线会拦下，不会发到 Release）。

想自己验：把 `cuobjdump.exe --list-elf llama-server.exe` 跑一遍（`cuobjdump` 在 CUDA 工具包的 `bin\` 里）。
注意 kernel **可能在 `ggml-cuda.dll` 里**而不是 exe 里，两个都要看。

### 7.5 构建产物什么时候能保住

流水线的顺序是：

```
编译 → 产物体检 → 组装发布包 → 上传 Artifact → 冒烟测试 → 架构硬校验 → 发布 Release
```

**体检不中断、硬闸放在上传之后**，是刻意的：一次 CUDA 全量编译要 30–40 分钟，
任何校验都不该让产物被丢掉。所以即使后面的判定失败，你仍然可以去 run 页面底部
下载 Artifact 自行排查，坏包也不会进 Release。

### 7.6 脚本逻辑全对、清单也打印了，步骤却是红的 —— `LASTEXITCODE` 传染 ★

**症状**：某一步的日志里能看到自己写的输出（比如产物清单表），逻辑显然跑完了，
但该步骤仍标记为 failure，后面所有步骤被 skipped，编了半小时的产物全被丢掉。

**原因**：GitHub Actions 对 `shell: pwsh` 的包装器会在你脚本的**末尾自动追加**：

```powershell
if ((Test-Path -LiteralPath variable:\LASTEXITCODE)) { exit $LASTEXITCODE }
```

也就是说，**步骤的退出码取决于最后一条「原生命令」的退出码**，而不是你的逻辑。
这条坑特别隐蔽，因为出问题的往往是无害的命令：

- `cuobjdump --list-elf 某个不含 CUDA 代码的 dll` → 返回非零
- `gh release view 一个还不存在的 tag` → 返回非零（哪怕你在 `if` 里判断过）
- `git rev-parse` 在非仓库目录 → 返回非零

本仓库实测就是这么栽的：体检步骤最后执行的是 `cuobjdump`（打包目录里绝大多数
exe/dll 都不含 CUDA 代码，一律返回非零），于是清单打印完、逻辑全对，步骤照样判失败。

**解法**：**每个调用过原生命令的 pwsh 步骤，末尾都要显式 `exit`。**

```powershell
# 体检 / 组装 / 冒烟 / 发布这类「成功即通过」的步骤 → 末尾收口
exit 0

# 真正的硬闸则显式给两个出口，别依赖 throw 之外的隐含行为
switch ($env:ARCH_OK) {
  'false'   { Write-Host "::error::判定不通过"; exit 1 }
  'unknown' { Write-Host "::warning::无法确认，放行"; exit 0 }
  default   { Write-Host "[OK] 通过"; exit 0 }
}
```

**通用判据**：只要 `run:` 里出现过 .exe（cuobjdump / gh / git / nvcc …），
就在末尾写 `exit 0`。花一行，省半小时。
