# V100 + 驱动 536.25 的 CUDA 预编译包调研

- 调研日期：2026-09-11
- 目标模型：`D:\llamacpp\models\Qwen3.8-27B-UD-Q4_K_M.gguf`（arch = `qwen35`）
- 约束条件：驱动 **536.25**（CUDA 12.2，PTX ISA ≤ 8.2）不能动；GPU 为 Tesla V100-PCIE-32GB（**sm_70 / Volta**）

---

## 一、直接回答

| 问题 | 答案 |
|---|---|
| 官方 llama.cpp 有 CUDA 12.2 的 Windows 预编译包吗？ | **没有，从来就没有过**（近 144 个 build，Windows CUDA 变体只有 `12.4 / 13.3 / 13.4`） |
| 第三方有 CUDA 12.2 的 Windows 预编译包吗？ | **有**（llama-cpp-python 的 `cu122` 索引），但**最晚只到 v0.3.4**，底层 llama.cpp 是 2024 年底的版本，**不认识 `qwen35`** → 对你没用 |
| 那到底有没有能用的？ | **有，两条**：① CUDA **11.8** 的第三方现行包（等效可用）；② 第三方仓库提供的**云端在线自编译**（可选 CUDA 12.2 + 指定 sm_70） |

> 一句话：你要的不是"12.2 这个数字"，而是"**PTX ISA ≤ 8.2 的 CUDA 后端**"。CUDA 11.8 同样满足，而且它在第三方生态里**还在持续维护**。

## 二、硬证据：为什么官方包在你的机器上必然失败

解剖本机 `D:\llamacpp\ggml-cuda.dll`（521.8 MB，build b10853）：

| 检测项 | 实测值 |
|---|---|
| CUDA fatbin 条目数 | 143 |
| 内嵌 **SASS（cubin ELF）** | **只有 2 个架构：`sm_86`、`sm_89`** |
| 内嵌 **PTX** | 6 个架构：`sm_50 / 61 / 70 / 75 / 80 / 90`，共 858 份 |
| PTX ISA 版本 | **8.4**（= CUDA 12.4） |
| 本机驱动 536.25 支持上限 | PTX ISA **8.2**（= CUDA 12.2） |

**推论链：**
1. V100 是 sm_70 → 包里**没有 sm_70 的 SASS**，只能走 PTX JIT；
2. PTX 是 8.4 编译的，驱动 536.25 最高只认 8.2 → JIT 失败 → `the provided PTX was compiled with an unsupported toolchain`；
3. CUDA 后端在**初始化阶段**就崩，所以 `-ngl 0`（纯 CPU）也一样崩，gpt-oss-20b 回归测试同样崩 —— 不是模型问题；
4. 官方 release 工作流（`.github/workflows/release.yml`）里**根本没有传 `CMAKE_CUDA_ARCHITECTURES`**，架构列表走 CMake 默认（老架构给 virtual/PTX、新架构给 real/SASS），工具链写死 `12.4 / 13.3 / 13.4`。

### 由此得到一条通用判据（后面所有方案都基于它）

> 在驱动 536.25 上，一份 llama.cpp CUDA 后端能否工作，只看两点：
> - **用 CUDA ≤ 12.2 工具链编译** → PTX ISA ≤ 8.2，驱动能 JIT → **一定能跑**（有没有 sm_70 SASS 都无所谓）；
> - **用 CUDA ≥ 12.3 编译** → 则**必须内嵌 sm_70 的 SASS（`-real`）**才能跑。
>
> 官方包两条都不满足 → 必然失败。

## 四、三条可执行方案

### 方案 A ★（推荐，最贴合你现有部署）— 云端自编译 CUDA 12.2 + sm_70

- 仓库：`jianlins/llama-cpp-custom-builds` → workflow `build-windows-cuda.yml`
- 参数：`repo=ggml-org/llama.cpp`、`llama_version=latest`、**`cuda_version=12.2.0`**、**`gpu_architectures=70`**、`build_type=Release`、`enable_cublas=true`
- 产物：单文件 `llama-server.exe`（可直接替换现有 `D:\llamacpp\llama-server.exe`，**bat 与 webui 一行都不用改**）
- **唯一坑**：该 workflow 的打包脚本**故意排除了 CUDA 运行时 DLL**（`cudart64_12.dll` / `cublas64_12.dll` / `cublasLt64_12.dll`），需另配。两个来源：
  1. 从 `llama-cpp-python` 的 **cu122 Windows 轮子（v0.3.4）**里取 —— 那个轮子正好是 CUDA 12.2，里面就带这三个 DLL（最省事）；
  2. 装 CUDA 12.2 的运行时组件。
- 需要你做的：把仓库 fork 到自己账号 → Actions → Run workflow → 等约 30–60 分钟 → 下载 artifact
- **我可以代做**：fork + 把"打包 CUDA 运行时 DLL"这一步补进 workflow，让它一次就产出**开箱即用**的压缩包。

### 方案 B（最快见效，代价最小的是改动）— `koboldcpp-oldpc.exe`

- 一个 460 MB 的 exe，自带 CUDA 11 运行时（不依赖你装任何东西），CUDA 11 → 驱动 536.25 完全满足；
- v1.120 release notes 已明确支持 Qwen3.8 家族；
- **代价**：换成了 KoboldCpp 自己的端口（5001）与 API/界面，`start-server-Qwen3827b.bat` 与 `webui` 需要改写适配。

### 方案 C（零成本，性能打折，需实测）— 官方 Vulkan 后端

- 下载官方 `llama-bXXXX-bin-win-vulkan-x64.zip`（与现有 CUDA 包同版本，**完整支持 qwen35**）；
- 驱动 536.25 自带 Vulkan 1.3 运行时，不需要额外装东西；
- **风险**：Tesla 卡处于 **TCC 模式**，Vulkan 设备**可能枚举不到**，必须先实测（值得花 5 分钟试一下）；
- 若可用：性能约为 CUDA 的 70–85%。

## 五、关于驱动（供参考，不动你的系统）

NVIDIA 官方开发者博客明确表述：

> *"The NVIDIA driver from branch 580 … will be the final branch that supports GPUs before CC 7.5."*
> 给 pre-CC 7.5 用户的官方建议：**驱动停在 580 分支 + CUDA 工具包停在 12.9。**

也就是说，按官方口径 **582.53（R580 分支）本应能识别 V100**。你那次不识别，**最可能的原因是安装包类型不对**，而不是版本问题：

- Tesla / 数据中心卡在 Windows 上需要 **Data Center(Tesla) 驱动包**，普通桌面 Game Ready / Studio 包在部分分支里不含 Tesla 设备 ID；
- 另有一种常见误装是 **vGPU 版驱动**（给虚拟机宿主机用的），裸机上必然不识别。

→ 建议核对一下当时那个 582.53 安装包的文件名/来源里是否含 `datacenter` / `tesla`。**若这条路走通，官方 CUDA 12.4 包可以直接用，不需要任何第三方方案。**

## 六、尚未实测确认的点（诚实标注）
