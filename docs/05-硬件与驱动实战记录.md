## 二、最大的坑：Tesla 卡上消费级主板的「代码 10」

### 现象

设备管理器里 V100 带黄色感叹号，属性显示：

```
该设备无法启动。(代码 10)
状态: 0xC000009A  =  STATUS_INSUFFICIENT_RESOURCES
```

`nvidia-smi` 报 `couldn't communicate with the NVIDIA driver`（这是**结果**，不是原因）。
驱动本身是好的（签名有效、INF 里 `DEV_1DB6` 精确匹配、`nvlddmkm.sys` 完好）。

### 定位过程（可复现）

三条关键证据：

1. **`setupapi.dev.log` 直接给出失败点**
   ```
   Device has problem: 0x0a (CM_PROB_FAILED_START), problem status: 0xc000009a
   ```
   → 说明设备枚举正常、驱动匹配正常，卡在**内核驱动启动阶段的资源分配**。

2. **量出平台 4GB 以上的 MMIO 窗口总量**
   把 `Win32_SystemMemoryResource` 的全部区间按地址排序，取 ≥4GiB 的部分：
   ```
   total reserved above 4GiB : 316.1 MB   (11 条区间，3 个簇)
   ```
   而 V100-PCIE-32GB 的 **BAR1 = 32 GB**。
   → **需求 : 供给 ≈ 104 : 1**，任何驱动、任何 Windows 侧操作都不可能凭空造出 32GB 连续窗口。
   窗口内最大连续空洞也只有 112 MB。

3. **故障发生在驱动 `StartDevice` 之前**
   `DevNodeStatus = 0x01802400`（`DN_HAS_PROBLEM` + `DN_PRIVATE_PROBLEM` 置位，
   `DN_STARTED` / `DN_DRIVER_LOADED` 未置位）。
   → 换 INF、换驱动分支**不改变固件给出的窗口大小**，所以"换驱动"是低价值路线。

### 处理与结论

- **BIOS 侧**（实际生效方向）：
  - `Re-Size BAR Support` → **Disabled**
    （机制：ReBAR 开启时走 32GB 对齐的大 BAR 协商，必然失败；关闭后退回小 BAR 模式。
    旁证：平台里恰好有一块**整 256.0 MB** 的窗口 `0x4000000000~0x400FFFFFFF`，与 256MB 级 BAR1 尺寸吻合）
  - `Above 4G Decoding` → **Enabled**
  - PCIe 链路速度 → 固定 **Gen3**
- **驱动侧**：最终可用的驱动是 **536.25**。
  - 已证实：`582.53`（R580 分支，官方口径上"应该"支持 Volta）在这张卡上**报代码 10**；
    退回 `536.25` 后正常识别并可用。
  - 未证实：这是"华为 OEM 卡个体差异"还是"R580 分支对这批卡的普遍问题"。
    官方论坛有同型案例（`DEV_1DB5&SUBSYS_124910DE`）：**旧驱动 462.30 可正常，551.78 与 582.70 均失败**。
  - **结论：显存卡能用哪版驱动，经验值不如实测值 —— 换驱动前先备份旧驱动包。**

### 可复用的排查命令（管理员 PowerShell）

```powershell
# 当前状态与问题码
Get-PnpDevice | Where-Object { $_.FriendlyName -like '*V100*' } |
    Format-List FriendlyName, Status, Problem, ProblemDescription

# 底层问题状态（0xC000009A = 资源不足）
Get-CimInstance -Namespace root\wmi -ClassName MSFT_...   # 或直接看 setupapi 日志

# 驱动安装失败的直接证据
Select-String -Path C:\Windows\INF\setupapi.dev.log -Pattern 'not started: Device has problem' |
    Select-Object -Last 5

# 量 4GiB 以上的固件预留窗口（判断 MMIO 空间够不够）
$r = Get-CimInstance Win32_SystemMemoryResource |
     Where-Object { $_.StartingAddress -ge 4294967296 } |
     Sort-Object StartingAddress
"count   = {0}" -f $r.Count
"total   = {0:N1} MB" -f (($r | Measure-Object -Property Capacity -Sum).Sum / 1MB)

# 重新枚举设备（不重启）
pnputil /scan-devices

# 指定 INF 安装
pnputil /add-driver "D:\drivers\nv_dispwi\nv_dispwi.inf" /install
```

## 三、驱动版本选择的实务建议

| 建议 | 依据 |
|---|---|
| **能用就不要动** | 本机正好是"新驱动反而认不到卡"的实例 |
| 换驱动前先把可用的那个完整备份下来 | 本机 `driver-backup\` 里存了 582.53 全套（含 `nvlddmkm.sys`），但真正能用的是 536.25 |
| Tesla 卡要用 **Data Center(Tesla) 驱动包** | 桌面 GeForce / Studio 包在部分分支里不含 Tesla 设备 ID；vGPU 版在裸机上必然不识别 |
| 用 `pnputil` 手动指定 INF，而不是让 Windows 自动挑 | `pnputil /add-driver "<路径>\nv_dispwi.inf" /install` |
| 堵住 Windows Update 自动推驱动 | `SearchOrderConfig=0`、`ExcludeWUDriversInQualityUpdate=1` |
| Volta 的支持终点 | NVIDIA 官方：**580 分支是最后支持 CC 7.0 的分支**，之后建议"驱动停 580 + CUDA 停 12.9" |

## 四、驱动不动的前提下，怎么让新版 llama.cpp 跑起来

这就是本仓库存在的理由。完整原理见 `docs/01`，结论：

```
CUDA 12.2.0 工具链  +  -DCMAKE_CUDA_ARCHITECTURES=70
```

- 用 CUDA 12.2 编 → PTX ISA ≤ 8.2，驱动 536.25 能 JIT
- 同时显式生成 sm_70 的 SASS → 连 JIT 都不需要，启动更快、更稳

实测过的失败组合（供参考，别再重复试）：

| 尝试 | 结果 |
|---|---|
| 官方包 + `-ngl 0`（纯 CPU） | **仍崩** —— CUDA 后端在初始化阶段就失败，跟用不用 GPU 无关 |
| 官方包 + 换模型（gpt-oss-20b 回归） | **仍崩** —— 证明不是模型问题 |
| 官方包 + `GGML_CUDA_PDL=0` | 报错从 `invalid device function` 变成 `unsupported toolchain`（暴露了真正原因） |
| 官方包 + 禁用 PTX JIT 强制走 SASS | `PTX JIT compilation was disabled` —— 因为包里**根本没有 sm_70 的 SASS** |
| 找官方 CUDA 12.2 的 Windows 预编译包 | **不存在**（近 144 个 build 只有 12.4 / 13.3 / 13.4） |

## 五、其他零散但有用的记录

- **`nvidia-smi` 的位置**：`C:\Windows\System32\nvidia-smi.exe`（DCH 驱动自带，不在别处）。
- **`C:\Windows\System32\drivers\nvlddmkm.sys` 不存在是正常的**：DCH 驱动用服务的
  `ImagePath` 直接指向 `DriverStore\FileRepository\...`。
- **TCC 模式**：Tesla 卡从"显示设备"变成"纯计算设备"。核显负责显示输出，两者不冲突。
- **不要在同一台机器上同时跑两个 llama-server**：显存不够，第二个必然 OOM。
- **模型加载速度取决于磁盘**：15.3 GB 权重从 NVMe 读进显存约 1–2 分钟，属正常。
- **网络**：本机访问 `github.com` 主站不通，但 `api.github.com`、`codeload.github.com`、
  `objects.githubusercontent.com` 通 —— 所以本仓库的下载脚本内置了 `gh-proxy.com` /
  `ghfast.top` / `ghproxy.net` 三个镜像做兜底。

2. 那块整 256MB 窗口与 V100 小 BAR1 模式的对应关系属于**推断**，未用 Linux Live USB 交叉验证。
